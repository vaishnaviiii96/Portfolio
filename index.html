The Problem

GITAM students preparing for placements had no structured way to access or analyze past interview experiences. Data was scattered in WhatsApp groups and informal notes — no trend analysis, no company-specific patterns, no way to know what topics actually come up at Amazon vs TCS.

What I Built

A full-stack placement prep platform: students submit interview experiences, faculty approve them, and the analytics layer surfaces company-specific trends, topic heatmaps, difficulty distributions, and contributor leaderboards. The 12-table PostgreSQL schema handles submissions, rounds, tags, comments, upvotes, bookmarks, and search analytics. Secure auth with OTP-based password reset and JWT sessions.

Testing & Reliability

Wrote 113 unit and integration tests (65 backend with Jest/Supertest, 48 frontend with Vitest/React Testing Library). This comprehensive test suite uncovered and fixed a critical production bug in the request validation middleware that would have caused API crashes on invalid input.

Impact

The heaviest analytics query (topic-frequency, joining multiple tables) took 728ms cold. I built a Redis-ready caching layer with automatic in-memory fallback — cache hits dropped to <1ms, a 99.9% reduction. Deployed to Render with a GitHub Actions CI pipeline on every push, rate-limited to handle production traffic reliably.

Trade-offs: Built with a per-process in-memory cache to avoid Redis overhead, though this limits horizontal scaling across multiple instances.

The Caching Problem in Detail

The analytics endpoint aggregates across submissions, rounds, round_tags, and tags tables — a multi-join query that hits Neon's serverless PostgreSQL over the network. Cold query time benchmarked at 728.38ms avg across 5 runs against the live DB. With analytics pages hitting this on every load, the UX was noticeably slow.

Technical Decision: Redis + In-Memory Fallback

Rather than just adding Redis (which requires a running Redis instance in every environment), I built a MemoryCache class that mirrors the Redis interface. The caching layer tries Redis first, falls back to in-memory if Redis is unavailable, and the rest of the code never knows the difference. Cache TTLs: 1 hour for analytics, 5 min for company routes, 1 min for submission lists.

Schema Design Decisions

The tag system uses a many-to-many join (round_tags) instead of a JSON column — this lets the analytics queries do proper GROUP BYs on topics without parsing. The search_logs table captures anonymized queries for the "search gaps" dashboard, revealing what students search for but don't find.

Trade-offs & What I'd Do Differently

  • Neon cold-start latency: The benchmark numbers (728ms) include the Neon serverless cold-start over the network from my machine. On Render co-located with Neon in us-east-1, real DB latency is 10-50ms. I'd add this context to any reported metric.
  • In-memory cache in production: The MemoryCache works per-process — multiple Render instances won't share cache state. In a scaled deployment, I'd require Redis (not the fallback) and use a managed Redis provider.
  • Full-text search: Current search uses LIKE across 4 fields. At scale, I'd migrate to PostgreSQL's built-in full-text search (tsvector/GIN index) or add Meilisearch.
  • Bundle size: The React bundle gzips to 246 KB. Recharts is a large dependency — I'd evaluate lighter alternatives like Visx or Chart.js for charts that don't need Recharts' advanced features.

The Problem

The university's certificate approval process was entirely paper-based. Students had to physically submit copies, which faculty manually verified and admins recorded. It was slow, error-prone, and provided no visibility into the approval status or historical data.

What I Built

A digitized role-based access control (RBAC) portal. Students upload certificates (processed via Cloudinary), faculty review them in queues, and admins export approved records to PDF/Excel. I implemented secure OTP password resets with 5-attempt lockouts and built a custom analytics dashboard with Chart.js.

Impact

Achieved a 98/100 Lighthouse performance score with 0ms Total Blocking Time on the frontend. During production, I actively traced and resolved three major infrastructure failures solo (SMTP outage, persistent volume loss, and proxy rate-limit misconfigurations), quickly restoring service with zero data loss.

Trade-offs: Chose Vanilla JS over React to minimize bundle size and blocking time, trading developer velocity for raw client performance.

RBAC and Security Design

The 3-tier RBAC system uses JWT payloads backed by live database flag checks for critical mutations. The password reset flow was engineered defensively: OTP codes are bcrypt-hashed in the database before storage, enforce a strict 10-minute expiry, and lock out accounts after 5 failed attempts to prevent brute-forcing.

Handling Production Outages

When the third-party SMTP provider experienced an outage, I immediately implemented a fallback queue to ensure password reset emails were preserved. I also diagnosed an issue where Cloudinary image uploads were failing on redeploys due to ephemeral file storage configurations, refactoring the upload pipeline to stream buffers directly to the cloud.

The Problem

Students needed a centralized place to publish project write-ups and share experiences, but a public feed poses moderation risks. Manual review of every submission would create a massive bottleneck for the admin team, delaying publication and discouraging use.

What I Built

A public feed platform where students can seamlessly publish their project stories. I integrated the Google Gemini API directly into the submission pipeline as a synchronous middleware. It analyzes the content, detects policy violations across multiple languages, and automatically flags inappropriate submissions before they ever hit the database.

Impact

Reduced manual moderation overhead to near-zero while maintaining feed safety. The core feed endpoint, despite the complex underlying database queries, sustains an average response time of ~84ms. The entire stack is continuously deployed to Render via GitHub Actions.

Trade-offs: Used synchronous API moderation on the critical path for simplicity, accepting higher submission latency instead of building an async queue system.

LLM Integration Architecture

Integrating Gemini API wasn't just an API call; it required strict prompt engineering to ensure the model returned deterministic, parsable JSON responses (e.g., {"approved": false, "reason": "..."}). I implemented circuit breakers in the middleware to default to an "under review" queue if the LLM API experienced timeouts or rate limits.

Authentication & Security

User sessions are managed via stateless JWTs to keep the API servers lightweight, but admin mutations require live database verification to prevent privilege escalation. For password resets, I utilized 256-bit cryptographically secure random tokens rather than basic OTPs, implementing anti-enumeration mechanisms on the user-check endpoints.
